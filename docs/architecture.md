# Архитектура FSP Talent

## 1. Функциональная архитектура

```
                    ┌──────────────── Кандидат ─────────────────┐
 Регистрация + e-mail → Профиль / PDF-резюме → Опрос (специализация, грейд)
        → Тест на заявленный грейд → Категория «Специализация · Грейд» (до 3, по одной на специализацию)
        → Обогащение из реестра ФСП → Публикация профиля (согласие 152-ФЗ)
        → Регулярные задания: система раз в неделю предлагает задачу от работодателя → свежий сигнал
                                                  │
                         верифицированный пул кандидатов
                                                  │
                    ┌──────────────── Работодатель ──────────────┐
 Профиль компании → Потребность (текст → структура) → Matching Engine
        → Подборка по категориям с объяснением → Профиль кандидата (без контактов)
        → Приглашение с зарплатной вилкой ──► Кандидат: просмотр → принять / отклонить
        → при принятии: раскрытие контактов работодателю (журнал раскрытий)

 Дополнительно: публичные вакансии + самостоятельный отклик, регулярные задания (адресные и
 челленджи категории, автопроверка и рубрика), проверка честности теста по поведению, жалобы на
 приглашения, дневной лимит приглашений.
```

Инициатива контакта — у работодателя (модель «обратного подбора», как в LHH): кандидат не рассылает
отклики, а получает предложения с условиями.

## 2. Компонентная архитектура

```
┌────────────┐    HTTPS/JSON     ┌──────────────────────────────────────────────┐    SQL    ┌────────────┐
│  Frontend  │ ───────────────►  │                 Backend API                  │ ────────► │ PostgreSQL │
│ React 19   │  /api (nginx      │ FastAPI · Pydantic · SQLAlchemy 2 · Alembic  │           │ (SQLite    │
│ TypeScript │   reverse proxy)  │                                              │           │  локально) │
└────────────┘                   │  api/          REST-роутеры (тонкие)         │           └────────────┘
      ▲  типы генерируются        │  services/     бизнес-сценарии               │
      │  из OpenAPI              │   ├ testing/   Testing Engine (чистый код)   │   SMTP    ┌──────────┐
      │                          │   ├ matching/  Matching Engine (чистый код)  │ ────────► │ Mailpit  │
      │                          │   ├ fsp/       порт реестра ФСП + адаптеры   │           └──────────┘
      │                          │   └ nlp/       разбор резюме / потребности   │
      │                          │  repositories/ доступ к данным               │   HTTP    ┌──────────┐
      │                          │  models/       ORM-модели                    │ ────────► │ Реестр   │
      │                          │  domain/       справочники, банк заданий     │ (адаптер) │ ФСП/мок  │
      │                          │  core/         конфиг, безопасность, ошибки  │           └──────────┘
      │                          └──────────────────────────────────────────────┘
      │
 evaluation/  — офлайн-валидация: используют те же модули testing/ и matching/ без БД
```

Монолит с явными слоями и слабо связанными модулями (допускается ТЗ). Testing Engine и Matching
Engine — **чистые функции над dataclass-ами** (`ItemSpec`, `CandidateFeatures`, `JobFeatures`), не
зависят от БД и HTTP: тот же код работает в API, в seed-данных и в скриптах валидации. Роутеры не
содержат бизнес-логики — только валидацию входа (Pydantic) и вызов сервиса.

### Слои backend

| Слой | Каталог | Ответственность |
|---|---|---|
| API | `backend/app/api` | REST-эндпоинты, зависимости аутентификации и ролей, документация ошибок |
| Схемы | `backend/app/schemas` | Pydantic-контракты запросов/ответов → OpenAPI → TypeScript-типы фронтенда |
| Сервисы | `backend/app/services` | Сценарии: регистрация, тестирование, подбор, приглашения, приватность |
| Движки | `services/testing`, `services/matching` | Генерация форм, IRT-оценка, правила грейдов; скоринг, объяснения |
| Репозитории | `backend/app/repositories` | Запросы с жадной загрузкой для ранжирования целых категорий |
| Модели | `backend/app/models` | 25 таблиц, ограничения целостности (CHECK, UNIQUE, FK) |
| Домен | `backend/app/domain` | Справочники специализаций/грейдов/навыков, банк заданий |

## 3. Модель данных

```
User 1─1 CandidateProfile 1─* CandidateSkill *─1 Skill
                │ 1─* CandidateCategory (специализация, грейд, θ, компетенции, блокировка; одна основная)
                │ 1─1 FSPProfile 1─* FSPAchievement
                │ 1─* TestAttempt 1─* TestItem 1─1 TestAnswer        (TestItem → Question)
                │                  1─1 TestResult
User 1─1 EmployerProfile 1─* Job (потребность / вакансия) 1─* JobSkill *─1 Skill
                                   │ 1─* MatchResult *─1 CandidateProfile   (снимок ранжирования)
EmployerProfile 1─* Invitation *─1 CandidateProfile   (Invitation → Job, необязательно)
Job 1─* Application *─1 CandidateProfile
EmployerProfile 1─* ShortTask 1─* TaskAssignment *─1 CandidateProfile   (адресное предложение)
                       │ 1─* TaskSubmission *─1 CandidateProfile    (автопроверка / рубрика)
ShortTask → Job (задание под потребность, необязательно)
ContactAccessLog (employer, candidate, reason) — журнал раскрытий контактов
Specialization 1─* Competency (план теста) · Grade (порог θ) · Question (версионируется)
```

Ключевые решения:
* **Job** объединяет «потребность» (приватную, для подбора) и «вакансию» (`is_public`) — приглашать
  можно без публикации, как требует ТЗ.
* **MatchResult** хранит снимок ранжирования: фильтры уточняют подборку, не теряя её и отметки
  «избранное»; снимок пересчитывается при изменении потребности или по TTL (5 минут).
* **TestItem** хранит отрисованный вариант вопроса (перемешанные варианты, параметры семейства) и
  правильный ответ — он никогда не уходит клиенту. Вопросы банка версионируются (`code`+`version`).
* Категории кандидата — `candidate_categories`: по одной на специализацию (Backend · Middle и
  DevOps · Junior), одна основная; у каждой свои θ, компетенции, блокировка смены грейда и «быстрая
  дорожка». Поля `verified_*` профиля зеркалят основную категорию. Пишет их **только** сервис
  тестирования. В подборке кандидата представляет категория специализации потребности (или ближайшая),
  навыки, подтверждённые в другой категории, тоже засчитываются как доказанные.
* Заявленный грейд (опрос) хранится отдельно и показывается со статусом: подтверждён тестом /
  подтверждён ниже / **не подтверждён** — официально грейд присваивает только тест.
* `test_attempts.integrity` — результат проверки честности по поведению, `test_answers.time_ms` и
  `pasted` — время на вопросе и вставка ответа.
* Зарплата обязательна: `CHECK salary_from > 0 AND salary_to >= salary_from` в `jobs` и `invitations`.

Миграции — Alembic (`backend/alembic/versions`), одинаково работают на PostgreSQL и SQLite.

## 4. Безопасность и приватность

* Пароли — bcrypt; токены — JWT HS256 с OIDC-совместимыми claims (`sub`, `email`, `iss`,
  `realm_access.roles`). Переход на **Keycloak / ФСП ID** — замена проверки подписи на JWKS (RS256)
  в `core/security.py::decode_access_token`; поле `users.external_subject` готово для связи учёток.
* RBAC: зависимости `Candidate` / `Employer` в `api/deps.py`; владелец ресурса проверяется в
  сервисах (чужая попытка теста, чужая потребность → 404, чтобы не раскрывать существование).
* Регистрация с подтверждением e-mail (6-значный код, хеш в БД, TTL 30 мин); вход без подтверждения
  запрещён. В демо-режиме (`EMAIL_DEV_EXPOSE_CODE=true`) код также возвращается API.
* 152-ФЗ: согласие на обработку — обязательно при регистрации; согласие на публикацию — отдельно, без
  него профиль не участвует в поиске; настройки видимости (фамилия, ФСП, зарплатные ожидания).
* Контакты кандидата раскрываются работодателю **только** после принятия его приглашения или
  самостоятельного отклика (`services/privacy.py`), каждое раскрытие пишется в `contact_access_log`.
  ФИО и профиль видны и до этого (по уточнению заказчика закрываются только контакты); кандидат может
  скрыть фамилию — тогда работодатель видит «Имя Ф.».
* Правильные ответы теста не покидают сервер; ответы валидируются по типу задания.
* Защита от спама: дневной лимит приглашений на работодателя (429), запрет дубликатов активных
  приглашений (409), ограничение ширины зарплатной вилки (≤ ×3), жалоба кандидата на приглашение.

## 5. Масштабирование и интеграции

* Stateless API (несколько воркеров uvicorn), состояние — в PostgreSQL. Ранжирование категории —
  O(N) по верифицированным кандидатам смежных специализаций с жадной загрузкой навыков/ФСП; снимок
  кэшируется в `match_results`. Для десятков тысяч кандидатов — предварительный отбор по категории в
  SQL и фоновой пересчёт снимков.
* Интеграция с реестром ФСП — через порт `FSPRegistry` (см. [fsp-integration.md](fsp-integration.md)).
* **ATS (концепция).** См. раздел 8.
* **Защита от фиктивных вакансий (концепция).** Скоринг доверия работодателя: верификация домена
  e-mail/ИНН, доля принятых приглашений, жалобы кандидатов (`invitations.reported`), аномалии вилок
  относительно рынка категории; при низком доверии — модерация приглашений и снижение лимита.
  В MVP реализованы: лимиты, валидация вилок, жалобы.

## 7. Локализация (RU / EN)

**Выбор языка.** Порядок: явный выбор на устройстве (переключатель RU / EN, `localStorage`) →
язык учётной записи (`users.locale`, восстанавливается при входе с другого устройства) → язык
браузера (`navigator.languages`) → русский. Выбор, сделанный вошедшим пользователем, сохраняется в
учётной записи (`PUT /api/auth/me/locale`); при регистрации записывается язык, на котором она прошла.

**Фронтенд** (`frontend/src/i18n`). Словари по разделам (`locales/ru/*`, `locales/en/*`);
английский словарь типизирован от русского, поэтому пропущенный ключ — ошибка компиляции.
Плюрализация — `Intl.PluralRules` (ru: one / few / many, en: one / other), числа, деньги и даты —
`Intl` (`ru-RU`, `en-GB`: порядок «день-месяц-год» в обоих языках). API-клиент отправляет
`Accept-Language` с каждым запросом, а `useApi` перезапрашивает данные при смене языка — тексты,
сформированные сервером (объяснения, причины, справочники), переключаются вместе с интерфейсом.
`<html lang>` обновляется для скринридеров. Тест `coverage.test.ts` запрещает русский текст в
компонентах вне словарей.

**Бэкенд** (`backend/app/i18n`). ASGI-middleware определяет язык запроса по `Accept-Language`
(с учётом q-весов) и кладёт его в контекстную переменную; сервисы вызывают `t(key, **params)`.
Ответ помечается `Content-Language` и `Vary: Accept-Language`. Ошибки 422 от Pydantic переводятся с
названием поля.

**Хранимые тексты не хранятся готовыми.** Снимок подборки (`match_results`) и причины в приглашении
сохраняются как объекты сообщений `{code, params}` с языконезависимыми параметрами (id, числа, имена
собственные; деньги — `{"money": n}`, навык — `{"skill": slug}`, дата — `{"date": …}`) и
отрисовываются при чтении: работодатель на английском и кандидат на русском видят одну и ту же
подборку каждый на своём языке. Рекомендация к результату теста выводится из сохранённого исхода.
Старые записи с готовым текстом отображаются как есть.

**Банк заданий.** Все 252 статических задания и 25 параметрических семейств есть на английском.
Перевод хранится в `questions.i18n` с тем же порядком вариантов, поэтому ключ ответа и IRT-калибровка
общие; семейства генерируют обе версии из одних случайных параметров. В попытке (`test_items.i18n`)
хранятся обе версии с одинаковой перестановкой вариантов — язык можно сменить посреди теста, ответы
остаются верными. Тесты проверяют полноту перевода, совпадение числа вариантов, неизменность
фрагментов кода и одинаковые числа в обеих версиях параметрических заданий.

**Разбор текста.** NLP-разбор потребности и резюме понимает оба языка: «желательно Redis» и
«Redis is a plus», «190–260 тыс.» и «from 150 to 200k», «опыт от 2 лет» и «2+ years».

Пользовательские данные (резюме, описания вакансий, названия соревнований из реестра ФСП)
показываются так, как их ввёл автор.

## 8. Интеграция с ATS работодателя (концепция)

По уточнению заказчика ATS-интеграция — это синхронизация вакансий, откликов и статусов с системой
найма работодателя через API, чтобы платформа встраивалась в существующий процесс. В MVP не требуется;
ниже — архитектурный подход, на который уже рассчитана модель данных.

| Объект | Направление | Как |
|---|---|---|
| Потребность / вакансия | ATS → платформа | `PUT /integrations/v1/requirements/{external_id}` — идемпотентный upsert по внешнему ID; текст разбирается тем же NLP, что и форма |
| Подборка | платформа → ATS | `GET /integrations/v1/requirements/{external_id}/matches` — ранжирование с объяснениями (контакты закрыты) |
| Приглашение / отклик | платформа → ATS | вебхуки `invitation.accepted`, `application.created` — профиль кандидата в стандартизированном JSON (как PDF-профиль) с контактами: на этом шаге кандидат дал согласие |
| Статусы | ATS → платформа | `POST /integrations/v1/applications/{id}/status` (interview / offer / hired / rejected) — кандидат видит статус; исходы — метки для дообучения весов подбора |
| Задания | ATS → платформа | создание регулярного задания под потребность тем же контрактом, что `POST /employer/tasks` |

* Аутентификация — API-ключ компании (хранится хешем, отзывается в кабинете) или OAuth2 client
  credentials; права — только своя компания.
* Вебхуки подписываются HMAC-SHA256 (`X-FSP-Signature`), доставка at-least-once с повторами и
  экспоненциальной задержкой, получатель дедуплицирует по `event_id`; журнал доставок в кабинете.
* Маппинг статусов настраивается (у каждой ATS свой справочник этапов); неизвестный статус не
  ломает синхронизацию, а сохраняется как «другое».
* Приватность не меняется: контакты уходят в ATS только после согласия кандидата (принятое
  приглашение или отклик), каждая передача пишется в `contact_access_log`.

## 9. NLP и LLM

Разбор резюме и описания потребности (RU / EN) — правила и словари (`services/nlp`), работают
локально, персональные данные не покидают контур. Заказчик допускает облачные LLM (в т.ч.
зарубежные, предпочтительнее открытые модели); если подключать модель для разбора свободного текста,
то открытую (класса 7–14B параметров) в своём контуре, а в облачную — только обезличенный текст
(ФИО, контакты и названия компаний заменяются метками до вызова), чтобы не возникала трансграничная
передача персональных данных по 152-ФЗ. Тесты и их оценка LLM не используют: генерация заданий
нейросетью не гарантирует сопоставимую сложность (ТЗ), поэтому задания калиброваны по IRT.

## 10. Фоновые задачи

Регулярные задания предлагаются фоновым проходом раз в `TASK_OFFER_LOOP_MINUTES` (по умолчанию 60) и
дополнительно при открытии кандидатом своих заданий или кабинета; проход идемпотентен (одно открытое
предложение на кандидата, уникальный индекс «задание–кандидат»), поэтому несколько воркеров не создают
дублей. Для продакшна с несколькими инстансами — вынести в планировщик (cron / очередь).
