# Уточнения заказчика и как они учтены

Ответы организаторов трека на вопросы команд и что по каждому изменено в решении. Ссылки ведут на
место в документации или код.

| # | Вопрос → ответ заказчика (кратко) | Что сделано |
|---|---|---|
| 1 | ФСП даёт буст внутри подтверждённого грейда, но не заменяет тест — **верно**. Дисциплины равноценны; можно учитывать актуальность направления (ИБ-специалист с соревнованиями по ИБ релевантнее, чем с робототехникой) | Логика не менялась: ФСП — 1 из 9 компонентов, грейд подтверждает только тест. Близость дисциплины к специализации потребности уже умножала вклад достижения — теперь она видна работодателю: «профильная / смежная дисциплина / другое направление» у каждого достижения и в объяснении («2 место — … · профильная дисциплина»). Базовые веса от дисциплины не зависят. [fsp-integration.md](fsp-integration.md#как-фсп-влияет-на-ранжирование) |
| 2 | Регулярные задания — **адресно** кандидату; челлендж на категорию не запрещён; способ оценки — на усмотрение команды | Система сама предлагает кандидату задание раз в неделю (одно открытое предложение, срок 7 дней) по правилу: соответствие грейду, работодатель рассматривает кандидата для потребности, к которой привязано задание, задание проверяет слабо подтверждённую компетенцию, новизна, нагрузка на проверку. Кандидат видит, почему задание его. Форматы: автопроверка (число / текст) и подход с предварительной оценкой по ключевым идеям и итоговой рубрикой работодателя (3 критерия × 0–2). Плюс челленджи категории и личное предложение от работодателя. Грейд задания не меняют. [testing.md §8](testing.md#8-регулярные-задания-servicestasks_servicepy) |
| 3 | Питч — 10 минут; видео вместо стенда допустимо; стенд держать на время оценки | Презентация перестроена под 10 минут (тайминг в заметках к слайдам), демо-видео сценария записывается скриптом `scripts/record_demo.py`; при отсутствии публичного стенда — `docker compose up --build` по [deployment.md](deployment.md) |
| 4 | Процедуру валидации стабильности предлагает команда: повторное прохождение одним профилем (test-retest) со сравнением грейдов + разделяющая сила заданий; симуляция допустима | Добавлено повторное прохождение **всей процедуры** одним профилем на непоказанных заданиях: совпадение грейда 75,9%, тот же или соседний 99,8%, κw 0,866, у уверенных результатов 88,2%. Разделяющая сила: индекс D и r_pb по каждому заданию (47% D ≥ 0,3, 24% — 0,2–0,3), критерии приёмки заданы заранее; скрипт `backend/scripts/item_analysis.py` повторяет анализ на реальных попытках. [testing.md §7](testing.md#7-валидация-python-evaluationevaluate_testspy) |
| 5 | Грейд — **уровень навыков**, подтверждаемый тестом; стаж — атрибут профиля | Описания грейдов переписаны через навыки (без «опыт до 1–2 лет»); стаж — отдельное поле, в подборке — отдельный фактор «опыт» |
| 6 | Одной категории достаточно; несколько — **плюс** | До 3 категорий, по одной на специализацию (`candidate_categories`): тест в новой специализации добавляет категорию, у каждой свои блокировка смены грейда и «быстрая дорожка», основную выбирает кандидат. В подборке кандидата представляет категория специализации потребности; навыки, подтверждённые в другой категории, засчитываются. [matching.md §2](matching.md#2-категоризация) |
| 7 | Облачные LLM допустимы (в т.ч. зарубежные), предпочтительны открытые; риски 152-ФЗ — на команде | LLM в решении не используется: разбор текста — локальные правила (данные не покидают контур). Политика на будущее: открытая модель в своём контуре, в облако — только обезличенный текст; тесты LLM не генерирует. [architecture.md §9](architecture.md#9-nlp-и-llm) |
| 8 | ФИО и места работы показывать допустимо; ТЗ закрывает только контакты до принятия приглашения / отклика | ФИО видно работодателю по умолчанию (кандидат может скрыть фамилию); контакты — по-прежнему только после согласия, с журналом раскрытий |
| 9 | Тест — единый под категорию при регистрации, но не одинаковый пул для всех; задания под вакансию — отдельный блок регулярных заданий | Так и устроено: индивидуальный вариант из банка по единому blueprint + параметрические семейства. Задание теперь можно привязать к потребности — оно уходит прежде всего кандидатам из её подборки |
| 10 | Лимитов на образ, модели, RAM нет; расход должен быть оправдан | Тяжёлых моделей нет: Python-сервис, PostgreSQL и статический фронтенд на лёгких базовых образах (`python:3.12-slim`, `nginx:alpine`); IRT, подбор и разбор текста считаются на CPU за миллисекунды |
| 11 | Качество подбора важнее скорости; «основные операции за приемлемое время» | Замеры: ранжирование 600 кандидатов под потребность — 57 мс, генерация варианта теста — 0,2 мс, оценка попытки — 3 мс (одно ядро) |
| 12 | Категории «специализация + грейд» достаточно; детальнее (стек, роль, формат) — плюс | Категория — «специализация · грейд», детализация — в профиле и подборке: стек с отметкой «подтверждён тестом», роли в команде, формат работы, несколько категорий |
| 13 | Грейд можно выбрать самому, но без теста — статус «грейд не подтверждён»; официально — только по тесту. Проверка на списывание — большой плюс | Статус заявленного грейда: «подтверждён / подтверждён ниже / **не подтверждён**» (кабинет, профиль; у работодателя в откликах — «Backend · Middle — грейд не подтверждён»). Списывание: к детектору утечки добавлена проверка поведения — уходы со вкладки, вставка, копирование, быстрые верные ответы на трудные для кандидата вопросы; «ищущих ответы на стороне» помечает в 99,8% случаев, «выучивших слитые ответы» — в 84,8%, честных — 0%. [testing.md §4а](testing.md#4а-проверка-честности-по-поведению-servicestestingintegritypy) |
| 14 | ATS — синхронизация вакансий, откликов, статусов через API; в MVP — концепция (доп. функционал) | Концепция расписана: объекты и направления синхронизации, идемпотентный upsert по внешнему ID, подписанные HMAC вебхуки с повторами, маппинг статусов, исходы найма как метки для дообучения подбора. [architecture.md §8](architecture.md#8-интеграция-с-ats-работодателя-концепция) |
| 15 | Данные — собственные (синтетика / открытые источники); парсинг не как продуктовая механика | Все данные синтетические, вакансии создают работодатели на платформе; парсинга чужих вакансий нет |
| 16 | Двух специализаций × двух грейдов достаточно, если сквозной путь работает; широта справочника оценку не поднимает | Справочник не расширялся (4 специализации × 3 грейда); усилия — в механику: категории, задания, проверка честности, валидация |
| 17 | Дизайнеров можно включить, приоритет — техническим ролям; идея объективного тестирования дизайнеров — плюс | Концепция: эвристическая оценка макета с эталонным списком дефектов, параметрические расчётные задания (контраст WCAG, сетка, шкалы), дизайн-системы и доступность, UX-метрики; портфолио — атрибут без влияния на грейд. [testing.md §9](testing.md#9-дизайнеры-как-тестировать-объективно-концепция) |
