# Механика подбора (Matching Engine)

## 1. Сценарий: обратный подбор

Кандидат **не откликается** на вакансии. Инициатива — у работодателя:

```
Потребность работодателя ──► Matching Engine ──► подборка по категориям ──► профиль кандидата
   (текст или форма)            (объяснимый           (рейтинг + почему)       (без контактов)
                                 скоринг)                                            │
          контакты кандидата ◄── кандидат принял ◄── кандидат видит компанию, ◄── приглашение
          (журнал раскрытий)                          предложение и ЗАРПЛАТУ        с вилкой
```

* Потребность не обязана быть опубликованной вакансией: приглашать можно напрямую.
* Описание потребности можно ввести текстом — NLP-разбор извлекает специализацию, грейд, стек,
  вилку, формат и опыт (`services/nlp/extractor.py`); работодатель проверяет и уточняет поля.
  Навыки после «желательно / приветствуется» или перед «будет плюсом» попадают в nice-to-have,
  остальные — в must-have; вилка «190–260 тыс.» понимается целиком, телефон не принимается за зарплату.
* Подборка сохраняется (`match_results`), фильтры уточняют её **без потери** (грейд, категория,
  обязательный навык, наличие ФСП, минимальный %, избранное); пересчёт — при изменении потребности,
  по TTL или кнопкой.
* Работодатель видит «рекомендованные категории» (Backend · Middle — 10 кандидатов, средний и
  максимальный %), затем конкретных людей в категориях.
* Сравнение «почему A выше B» — разложение разницы по факторам (`GET …/compare`).
* Приглашение: должность, описание, **обязательная вилка от–до в ₽**, формат, способ связи; статусы
  `sent → viewed → accepted | rejected`, а также `expired` (14 дней) и `withdrawn`.
* Кандидат видит условия и «почему выбрали вас» до ответа; контакты раскрываются только после
  принятия (или если кандидат сам откликнулся на вакансию).

Дополнительно: банк кандидатов (вся база с фильтрами, сортировка внутри категории по силе
подтверждённого профиля), публичные вакансии с обратным матчингом для кандидата (% совпадения у
каждой вакансии), отклики, короткие задания.

## 2. Категоризация

Категория = **подтверждённая специализация · подтверждённый грейд** (Backend · Middle и т.д.),
присваивается только тестированием (см. [testing.md](testing.md)). Кандидат может подтвердить до трёх
категорий — по одной на специализацию (Backend · Middle и DevOps · Junior). В подборке кандидата
представляет категория специализации потребности (если её нет — ближайшая по матрице смежности
специализаций): её грейд, θ и компетенции идут в формулу, а навыки, подтверждённые тестом в другой
категории, тоже считаются доказанными. Кандидат без подтверждённой категории или без согласия на
публикацию в подборки не попадает. Внутри категории кандидаты ранжируются по силе подтверждённого
профиля — ФСП усиливает ранжирование внутри подтверждённого грейда, но не заменяет тест (заказчик
подтвердил эту логику):

```
profile_strength = 0.6 · σ(1.7·(θ − порог грейда)) + 0.25 · ФСП + 0.15 · актуальность
```

## 3. Формула совпадения

```
match = gate_must × Σ_k w_k · s_k / Σ_k w_k         по ДОСТУПНЫМ компонентам k,  s_k ∈ [0, 1]
```

| k | Компонент | Вес | Как считается |
|---|---|---|---|
| skills | Стек и навыки | 0.26 | 0.75·покрытие must + 0.25·nice. Каждый требуемый навык ищется через **граф навыков** (FastAPI ≈ Flask 0.7, PostgreSQL ≈ MySQL 0.65, React ≈ Next.js 0.75 …) и умножается на **доказательность**: заявленный уровень × (0.75 + 0.25·балл теста по компетенции, которая этот навык проверяет) |
| grade | Грейд | 0.22 | совпадает 1.0; выше на 1 — 0.6; ниже на 1 — 0.4 (0.6 если тест показал готовность к повышению); разница ≥ 2 — исключение |
| test | Результат теста | 0.16 | 0.65·σ(1.7·(min(θ, порог+1) − порог требуемого грейда)) + 0.35·средний балл компетенций, релевантных стеку. Способность выше следующего грейда не даёт бонуса (переквалификацию учитывает «грейд») |
| specialization | Специализация | 0.10 | совпадает 1.0; смежная — частично (Backend↔DevOps 0.35, Backend↔Data 0.25…); несмежная — исключение |
| fsp | Достижения ФСП | 0.10 | 0.3 + 0.7·сила; **нет истории → 0.3 (нейтрально, без штрафа)** |
| freshness | Актуальность профиля | 0.06 | 0.5^(дней с последней активности / 120); активность — тест, ответ на приглашение, короткое задание |
| salary | Зарплатные ожидания | 0.05 | в вилке — 1; выше — линейный спад до 0 при превышении на 40%; не указаны — компонент недоступен |
| experience | Опыт | 0.03 | min(1, опыт / требуемый); требование не задано — недоступен |
| format | Формат работы | 0.02 | матрица совместимости remote/office/hybrid + город |

* **Нет данных ≠ 0.** Недоступные компоненты (не указаны ожидания по зарплате, нет требования к опыту)
  исключаются, а веса перенормируются. ФСП всегда «доступен» через нейтральную базу.
* **Мягкое «И» для обязательных навыков**: `gate_must = min(1, (0.8 + 0.2·покрытие_must) / 0.92)` —
  отсутствие обязательных навыков масштабирует весь балл, чтобы сильный тест не маскировал отсутствие
  того, что работодатель явно требует.
* Жёсткие фильтры: несмежная специализация, разница грейдов ≥ 2, итог ниже 35%.
* При равенстве баллов выше тот, у кого выше θ, затем — сильнее ФСП.

Профили весов на выбор работодателя: **Сбалансированный** (по умолчанию), **Сначала стек**
(skills 0.40), **Подтверждённый талант** (test 0.30, ФСП 0.18). Веса переопределяются через
`MATCHING_WEIGHTS_JSON`. Код: `backend/app/services/matching/engine.py`, `config.py`.

### Почему такие веса

* Стек (0.26) — главный язык, которым работодатель описывает потребность, но навык учитывается по
  доказательности, а не по факту упоминания в резюме.
* Грейд (0.22) — центральная часть категории; подобран на бенчмарке (п. 6): недо- и переквалификация —
  основные причины нерелевантной выдачи.
* Тест (0.16) — сопоставимая (IRT) мера уровня относительно требуемого грейда.
* Специализация (0.10) — в основном работает как фильтр, частичный балл только для смежных профилей.
* ФСП (0.10) — проверяемый сигнал практических навыков; заметно поднимает внутри категории, но не
  может перевесить стек и грейд; нейтральная база исключает дискриминацию тех, кто не участвовал.
* Актуальность, зарплата, опыт, формат — небольшие поправки (самоописанный опыт — сознательно 0.03).

## 4. Объяснимость

Каждый результат содержит:
* **причины** — человекочитаемые утверждения с типом (✓ плюс / • нейтрально / ✗ минус):
  «Подтверждённый грейд Middle — как требуется», «Совместимость стека 82%: 4 из 4 обязательных
  навыков, 4 подтверждены тестом», «Близкие навыки: Flask вместо FastAPI», «Нет истории ФСП — сигнал
  не учитывается, без штрафа», «Ожидания 410 000 ₽ — выше вилки на 64%»;
* **разложение балла** — оценка, вес и вклад каждого фактора в итоговые проценты (сумма вкладов =
  итог), множитель покрытия обязательных навыков;
* **сопоставление навыков** — точное совпадение / близкий навык / отсутствует, подтверждён ли тестом;
* **сравнение двух кандидатов** — разница вкладов по факторам и текстовое резюме
  («Разница +8 п. Преимущество: грейд (+8.8), стек и навыки (+2.3). Уступает: достижения ФСП (−1.2)»).

* **свежий сигнал** — если кандидат недавно выполнил регулярное задание: «Свежий сигнал: задание
  „Идемпотентность платежей“ — 83%, 3 дня назад»; на карточке — «Задания: 3 · средний балл 83%»;
* **достижения ФСП с профильностью** — «2 место — Всероссийские соревнования… (2026) · профильная
  дисциплина»: все дисциплины ФСП равноценны, но вес достижения зависит от близости дисциплины к
  специализации потребности (см. [fsp-integration.md](fsp-integration.md)).

Кандидат в приглашении видит процент совпадения и положительные причины — почему выбрали его.

## 5. Приватность в подборе

До контакта работодатель видит ФИО (кандидат может скрыть фамилию — «Имя Ф.»), категории, тест,
навыки, ФСП, город, ожидания (если кандидат разрешил). Контакты — только после принятия приглашения или отклика. Скрытые кандидатом
данные (ФСП, зарплата) не используются и в ранжировании.

## 6. Валидация (`python evaluation/evaluate_matching.py`)

Готового датасета нет, поэтому построен **синтетический бенчмарк со скрытой истиной**: 60 потребностей
× 600 кандидатов. У кандидата есть скрытый «истинный» профиль (специализация, способность θ, реальные
навыки); движок видит только наблюдаемое:

* резюме: истинные навыки с пропусками (10%) и **«приписанными» модными навыками своей области**
  у 40% кандидатов (keyword stuffing — именно проблема, описанная в ТЗ);
* самооценка грейда: завышение на уровень у 30%, занижение у 10%;
* результат теста: θ с погрешностью 20-заданной формы (SE ≈ 0.33) и баллы компетенций;
* ФСП: у ~50%, сильнее у сильных; зарплатные ожидания, формат, активность.

Метки релевантности 0–3 назначаются **экспертными правилами по скрытому профилю** (полезность найма:
специализация × соответствие истинного грейда × реальное покрытие must-have × сила внутри грейда ×
совместимость по зарплате) — без использования весов движка. Релевантен кандидат с меткой ≥ 2.

| Ранжировщик | P@5 | P@10 | R@10 | MRR | NDCG@10 |
|---|---|---|---|---|---|
| Случайный (та же специализация) | 0.193 | 0.202 | 0.062 | 0.311 | 0.168 |
| Поиск по ключевым словам резюме («классическая площадка») | 0.377 | 0.412 | 0.169 | 0.655 | 0.461 |
| Ключевые слова + заявленный грейд | 0.700 | 0.608 | 0.273 | 0.817 | 0.692 |
| **FSP Talent (сбалансированный)** | **0.880** | **0.807** | **0.346** | **0.933** | **0.808** |
| — без тестирования (самооценка грейда) | 0.813 | 0.747 | 0.325 | 0.929 | 0.771 |
| — только подтверждённый грейд (без θ и компетенций) | 0.887 | 0.817 | 0.352 | 0.992 | 0.833 |
| — без графа навыков | 0.873 | 0.782 | 0.343 | 0.958 | 0.824 |
| — без сигнала ФСП | 0.890 | 0.818 | 0.352 | 0.942 | 0.819 |
| — без мягкого «И» для must-have | 0.883 | 0.808 | 0.345 | 0.933 | 0.804 |
| Профиль «Сначала стек» | 0.717 | 0.662 | 0.302 | 0.795 | 0.674 |
| Профиль «Подтверждённый талант» | 0.673 | 0.625 | 0.287 | 0.816 | 0.631 |

Выводы:
* Движок существенно превосходит поиск по ключевым словам (NDCG@10 0.81 против 0.46) и даже поиск
  с учётом самооценки грейда (0.69): в топ-5 релевантны 88% кандидатов против 38% и 70%.
* Тестирование даёт прирост: с самооценкой грейда вместо подтверждённого NDCG падает до 0.77.
* Честно о слабых местах: в этой разметке сила внутри грейда влияет слабо (±15%), поэтому
  упорядочивание по θ внутри категории даёт −0.025 NDCG относительно «только грейд»; граф навыков и
  ФСП в синтетике почти нейтральны (метки не содержат ФСП, «близкие» навыки редки). Эти компоненты
  оставлены ради объяснимости и требований ТЗ («выше те, у кого сильнее подтверждённый профиль и есть
  опыт ФСП»), их веса умеренные.
* **Справедливость к кандидатам без ФСП**: идеальные (метка 3) кандидаты без истории ФСП в среднем на
  4,5-м перцентиле выдачи, с ФСП — на 3,6-м: ФСП помогает, но отсутствие не «топит».

### Подбор гиперпараметров (`python evaluation/tune_matching.py`)

Сетка (минимум мягкого «И», сила тестовой доказательности навыков, доля компетенций в компоненте
теста, 3 варианта весов) на обучающем мире (seed 11), проверка на **независимом** мире (seed 23):

| Конфигурация | NDCG@10 train | NDCG@10 held-out | P@10 held-out | MRR held-out |
|---|---|---|---|---|
| Исходная экспертная (v1.0) | 0.624 | 0.594 | 0.573 | 0.797 |
| Лучшая на сетке (gate 0.8, evidence 0, grade 0.22) | 0.832 | 0.809 | 0.792 | 0.967 |
| **Принятая в продукт (v1.2, evidence 0.25)** | **0.808** | **0.786** | **0.770** | **0.956** |

Прирост на независимых данных сохраняется (0.594 → 0.786), значит подбор не переобучен на одну
синтетическую выборку. Сила тестовой доказательности навыков оставлена 0.25 вместо оптимальных 0:
«навыки, подтверждённые тестом, весят больше» — продуктовый стимул проходить тест; цена — 0.023 NDCG
на отложенных данных. Полный отчёт: `evaluation/results/tuning_report.md`.

Скорость: ранжирование всего пула (600 кандидатов) под одну потребность — признаки, 9 компонентов
и объяснения — **57 мс** на одном ядре; подборка сохраняется снимком (заказчику важнее качество подбора,
чем скорость; основные операции укладываются в доли секунды).

Свой набор пар «вакансия — кандидат» можно проверить командой
`python evaluation/evaluate_matching.py --dataset my_pairs.json` (формат — как у
`evaluation/data/matching_benchmark.json`, экспортируемого скриптом).

## 7. Ограничения и развитие

* Веса подобраны на синтетике; после запуска — дообучение на реальных исходах (приглашение →
  принятие → найм) как learning-to-rank с теми же признаками; объяснимость сохраняется (линейная модель
  над интерпретируемыми компонентами).
* Граф навыков — экспертный; может пополняться эмбеддингами совместной встречаемости навыков.
* Регулярные задания сейчас влияют на актуальность и дают «свежий сигнал» в объяснении; когда
  накопится статистика, оценки можно сделать отдельным компонентом «подтверждённые практические
  задачи» с весом, подобранным на исходах приглашений.
