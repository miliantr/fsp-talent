# Механика тестирования и категоризации

## Требования ТЗ и как они закрыты

| Требование | Решение |
|---|---|
| Единый набор заданий не подходит — разойдётся | Каждому кандидату генерируется свой вариант из банка (сейчас 252 статических задания + 25 параметрических семейств) |
| Генерация нейросетью не гарантирует сопоставимую сложность | Варианты собираются по **единому плану (blueprint)**: одинаковое число заданий по компетенциям и одинаковый профиль сложности; оценка по **IRT** учитывает сложность конкретных заданий |
| Категория — не из самоописания, а через опрос → выбор грейда → тест | Категория `Специализация · Грейд` меняется только сервисом тестирования |
| Грейд не понижается принудительно; можно тест ниже/выше | Провал заявленного грейда → тест ниже доступен сразу; уверенный результат → тест выше без ожидания |
| Смена грейда ограничена по времени | Не чаще раза в 90 дней (`grade_locked_until`), повтор того же теста — через 30 дней |
| Грейд — уровень навыков, подтверждённый тестом (уточнение заказчика) | Заявленный в опросе грейд показывается со статусом «подтверждён / подтверждён ниже / **не подтверждён**»; официально грейд присваивает только тест, стаж — отдельный атрибут профиля |
| Несколько категорий — плюс (уточнение) | До 3 категорий, по одной на специализацию; у каждой своя блокировка и «быстрая дорожка», одна основная |
| Проверка на списывание — большой плюс (уточнение) | Детектор утечки (что ответил) + проверка поведения (как отвечал): уходы со вкладки, вставка, копирование, быстрые верные ответы на трудные вопросы |
| Процедура валидации — тест–ретест и разделяющая сила заданий (уточнение) | Раздел 7: повторное прохождение всей процедуры одним профилем, индекс D и r_pb по каждому заданию, скрипт для реальных данных |
| Регулярные задания — адресно, оценка на усмотрение команды (уточнение) | Раздел 8: система предлагает задачу конкретному кандидату; автопроверка или рубрика работодателя |

## 1. Банк заданий

`backend/app/domain/question_bank/` — 4 специализации × 5–6 компетенций, уровни сложности 1–5:

| Специализация | Компетенции (доля в плане теста) |
|---|---|
| Backend | язык и рантайм 22%, БД и SQL 20%, API/HTTP/безопасность 18%, архитектура 18%, алгоритмы 12%, эксплуатация 10% |
| Frontend | JS/TS 26%, React и состояние 24%, HTML/CSS/a11y 18%, браузер и производительность 18%, тесты и сборка 14% |
| Data / ML | классическое ML 26%, статистика 20%, данные (SQL, pandas) 20%, DL 18%, MLOps 16% |
| DevOps | контейнеры и оркестрация 24%, Linux и сети 22%, CI/CD и IaC 20%, мониторинг 18%, облака и безопасность 16% |

Метаданные задания (`questions`): `code`, `version`, `specialization`, `competency`, `difficulty`,
`qtype` (single / multi / numeric), варианты, правильный ответ, IRT-параметры `a`, `b`, `c`,
счётчик показов `exposure_count`, `family` для параметрических шаблонов. Изменение содержимого создаёт
новую версию (старая деактивируется, попытки ссылаются на точную версию).

**Параметрические семейства** (`families.py`, `families_extra.py`) — шаблоны с фиксированной
когнитивной операцией и сложностью, у которых при каждом показе меняются параметры: длина `range()`,
число сравнений бинарного поиска, асимптотика циклов, строки после `GROUP BY … HAVING`, `LEFT JOIN`,
специфичность CSS-селектора, батчинг `setState`, semver-диапазоны, precision/recall/F1, теорема Байеса,
размер выхода свёртки, CIDR, chmod, бюджет простоя SLO, ёмкость узла Kubernetes, формула HPA и др.
Ответ одного кандидата бесполезен следующему: у него другие числа. Семейства покрывают все 21
компетенцию.

**Языки.** Каждое задание банка есть на русском и английском (`question_bank/en_*.py`, по коду
задания). Варианты ответа идут в том же порядке, фрагменты кода не меняются, поэтому правильный
ответ и параметры IRT общие. Параметрические семейства формируют обе версии из одного набора
случайных параметров. Кандидат проходит тест на языке интерфейса и может переключить язык посреди
попытки — вопросы придут в переводе, данные ответы останутся засчитанными.

## 2. Генерация варианта (`services/testing/generator.py`)

1. **Blueprint** для (специализация, целевой грейд, длина = 20):
   * квоты компетенций — по долям плана (метод наибольших остатков, минимум 1);
   * профиль сложности сконцентрирован у порогов решения грейда (там нужна максимальная
     информативность теста):

     | Цель | ур.1 | ур.2 | ур.3 | ур.4 | ур.5 |
     |---|---|---|---|---|---|
     | Junior | 20% | 40% | 33% | 7% | — |
     | Middle | — | 20% | 40% | 33% | 7% |
     | Senior | — | — | 25% | 45% | 30% |
   * уровни распределяются по компетенциям детерминированно (Сент-Лагю), так что у каждой
     компетенции есть лёгкие и трудные слоты. **План одинаков для всех кандидатов.**
2. **Заполнение слотов**: для каждого слота случайно выбирается задание той же компетенции и
   сложности; приоритет — редко показанным (вес `1/(1+показы)`, контроль экспозиции), параметрические
   семейства предпочитаются (вес 3, утечка им не страшна). Задания, уже виденные кандидатом, исключаются.
   Если ячейка пуста — берётся ближайший уровень в сторону, компенсирующую накопленный сдвиг
   сложности, поэтому средняя сложность формы остаётся равной плановой.
3. **Отрисовка**: случайный порядок заданий, перемешанные варианты ответов, новые параметры семейств.
   Правильные ответы хранятся на сервере (`test_items.correct`) и никогда не отправляются клиенту.

## 3. Оценка (`services/testing/irt.py`, `scoring.py`)

* Модель 3PL: `P(верно | θ) = c + (1 − c) / (1 + e^(−1.7·a·(θ − b)))`; начальные параметры — из
  экспертного уровня сложности (`b ∈ {−2, −1, 0, 1, 2}`) и формата (`a` = 1.0 / 1.3 / 1.4,
  `c` = 0.8/k для выбора из k, 0.05 для множественного выбора, 0 для числового ответа).
* Способность θ оценивается методом **EAP** (апостериорное среднее на сетке θ ∈ [−4; 4], априорно
  N(0; 1.25²)) — конечна даже при всех верных/неверных ответах; апостериорное СКО — погрешность.
* Пороги грейдов на шкале θ: Junior −1, Middle 0, Senior +1. Публичная шкала **0–100 = 50 + 25·θ**,
  пороги читаются как 25 / 50 / 75 баллов. Шкальный балл сопоставим между разными вариантами, в
  отличие от «% верных».
* **Решение**: грейд подтверждён, если `P(θ ≥ порог | ответы) ≥ 0.5`; «уверенный результат» (открывает
  тест на грейд выше без ожидания), если `P(θ ≥ порог следующего грейда) ≥ 0.8`. Уверенность решения —
  соответствующая апостериорная вероятность.
* Профиль компетенций — доля баллов по каждой компетенции (с частичным зачётом множественного выбора).
* Категория = `верифицированная специализация · подтверждённый грейд`.

## 4. Детектор утечки (защита от «слитых» ответов)

Кандидат, выучивший ответы, отвечает неправдоподобно: верно на трудные «известные» задания и неверно
на свежие. Два статистических признака (`scoring.py`):

* **person-fit lz\*** (Drasgow, 1985) — стандартизованное правдоподобие паттерна ответов; порог −2;
* **разрыв способностей**: θ по статическим заданиям минус θ по параметрическим (неутекаемым), в
  единицах погрешности; порог 1.9.

Помеченный результат не присваивает грейд: кандидату сразу доступна **одна подтверждающая форма** из
непоказанных ему заданий (без кулдауна). Честные кандидаты помечаются в 4,7% случаев и просто
проходят ещё одну форму.

## 4а. Проверка честности по поведению (`services/testing/integrity.py`)

Детектор утечки смотрит, **что** ответил кандидат; эта проверка — **как** он отвечал. Страница теста
открыто (кандидат предупреждён в начале теста; камера, микрофон и экран не используются) передаёт с
каждым ответом:

* уходы со вкладки теста — число и суммарное время вне вкладки;
* копирование текста вопроса и вставку ответа из буфера обмена;
* время на вопросе, пока вкладка видима.

При завершении сервер складывает баллы риска: уходы со вкладки (3+ → 1, 8+ → 2), доля времени вне
вкладки ≥ 25% → 1, вставки (1+ → 1, 3+ → 2), копирования 2+ → 1, и **быстрые верные ответы на
вопросы, трудные для этого кандидата**: P(верно | θ_ref) < 0,35, а ответ дан быстрее четверти
ожидаемого времени задания (2+ → 1, 4+ → 3). Это сигнатура заранее известного ответа по времени
реакции (van der Linden & Guo, 2008). θ_ref оценивается **только по параметрическим заданиям** —
их ответы нельзя выучить, поэтому утечка не завышает эталонную способность.

Итог: `ok` (0 баллов), `attention` (1–2: замечание без последствий) или `risk` (3+). Один сигнал ничего
не решает. Результат с риском не отклоняется: как и при флаге утечки, кандидату сразу доступна одна
подтверждающая форма, грейд не теряется. Кандидат видит, что именно замечено. Счётчики
накопительные, сервер хранит максимум — перезагрузка страницы их не сбрасывает.

## 5. Правила грейдов и кулдауны (`services/testing/policy.py`)

* одна активная попытка; лимит времени 30 минут (просроченные завершаются автоматически с данными
  ответами);
* тот же (специализация, грейд) — повтор через 30 дней;
* без подтверждённого грейда: провалили Middle → тест на Junior доступен сразу (профиль не
  блокируется и не удаляется);
* подтверждённый грейд меняется не чаще раза в 90 дней, кроме «быстрой дорожки»: уверенный результат
  открывает тест на следующий грейд сразу;
* проваленный тест на повышение **не понижает** грейд; переподтверждение текущего грейда обновляет
  актуальность профиля;
* тест в другой специализации **добавляет** категорию (до 3), не заменяя имеющуюся; у каждой
  категории свои блокировка смены грейда и «быстрая дорожка»; основную кандидат выбирает сам.

Все сроки настраиваются переменными окружения.

## 6. Устойчивость к распространению заданий — итог

1. Вариант у каждого свой (пересечение соседних вариантов ~30–50% по статическим заданиям), порядок и
   варианты ответов перемешаны.
2. Параметрические семейства не утекают по построению; их доля в варианте повышена.
3. Контроль экспозиции распределяет показы по банку; исключаются уже виденные задания.
4. IRT позволяет постоянно пополнять банк: новые задания калибруются по ответам (см. п. 7 валидации)
   и сразу становятся взаимозаменяемыми со старыми.
5. Детектор утечки + подтверждающая форма.
6. Проверка поведения: уходы со вкладки, вставка, быстрые верные ответы на трудные вопросы (п. 4а).
7. Регулярные задания от работодателей дают независимый «свежий» сигнал (п. 8).

## 7. Валидация (`python evaluation/evaluate_tests.py`)

### Процедура

Эталонной разметки нет, поэтому валидность проверяется **симуляцией с известной истиной** — это
допускает и заказчик («допустима симуляция на синтетических кандидатах»):

1. **Популяция.** 400 синтетических кандидатов на каждую из 4 специализаций с истинной способностью θ
   и, значит, истинным грейдом (θ < −1 — ниже Junior, [−1; 0) — Junior, [0; 1) — Middle, ≥ 1 — Senior);
   10% ниже Junior, 20% заявляют грейд выше реального.
2. **Ответы без круговой логики.** Ответы генерируются по 3PL с **истинными** параметрами заданий,
   которые отличаются от номинальных (`b + N(0; 0,35)`, `a · LogN(0; 0,2)`); движок оценивает по
   номинальным — проверка включает ошибку модели.
3. **Продакшн-код целиком:** blueprint → генерация варианта → оценка → правила грейдов → подтверждающая
   форма при флаге.
4. **Метрики** по критериям ТЗ: соответствие эталону (истинному грейду), стабильность грейда при
   повторном прохождении, разделяющая сила заданий, устойчивость к утечке и списыванию,
   эквивалентность вариантов.
5. **Критерии приёмки**, заданные до прогона: взвешенная κ с эталоном ≥ 0,8; завышение грейда ≤ 5%;
   повторное прохождение — тот же грейд или соседний ≥ 95%; ≥ 2/3 заданий с D ≥ 0,2; пройденность
   «слитого» теста с детектором ≤ 25% при одном слитом варианте; ложные пометки честных ≤ 5%.
6. **На реальных данных** та же процедура повторяется на пилоте: `python backend/scripts/item_analysis.py`
   считает p, r_pb и индекс D по каждому заданию из сохранённых попыток и помечает задания на
   пересмотр; тест–ретест — добровольцы проходят тест повторно через 2–4 недели;
   экспертная валидация — сравнение грейда с оценкой технического интервью на выборке нанятых.

### Стабильность грейда при повторном прохождении (тест–ретест)

Тот же профиль **дважды проходит всю процедуру** (тест на заявленный грейд → при неудаче тест ниже →
подтверждающая форма при флаге), во второй раз — на заданиях, которых ещё не видел. Сравниваются
присвоенные грейды:

| Метрика | Значение |
|---|---|
| Совпадение присвоенного грейда | **75,9%** |
| Тот же или соседний грейд | **99,8%** (критерий ≥ 95% ✓) |
| Взвешенная κ между прохождениями | **0,866** |
| Совпадение, если оба результата уверенные (≥ 0,8; таких 57%) | **88,2%** |
| Совпадение, если θ дальше 0,25 от порога грейда (59% кандидатов) | 82,6% |
| Совпадение у пограничных (\|θ − порог\| < 0,25) | 66,3% |
| Корреляция θ на двух параллельных формах одного грейда | 0,874 |

Расхождения сосредоточены у порогов грейда — там, где и эксперт колебался бы. Поэтому результат
показывается вместе с **уверенностью** (вероятность, что θ выше порога), а работодатель видит её в
профиле. Повторная сдача того же грейда — не раньше чем через 30 дней, смена — не чаще раза в 90 дней:
перебором форм «дотянуть» грейд нельзя.

`item_analysis.py` выводит первыми — их переписывают, перекалибруют или выводят из банка.

### Утечка и списывание

Утечка: кандидат уровня Junior (θ = −0,4) заранее знает ответы K «слитых» вариантов теста Middle.
Доля сдавших:

| K | Единый тест для всех | Генерируемые формы | Формы + детектор + подтверждение |
|---|---|---|---|
| 0 | 7,7% | 8,3% | 6,7% |
| 1 | 98,7% | 44,3% | **23,0%** |
| 3 | 98,3% | 82,7% | **12,0%** |
| 10 | 98,3% | 97,0% | **1,3%** |

Проверка поведения (п. 4а). Модель времени ответа — ожидаемое время задания × логнормальный шум.
Уровень Junior (θ ∈ [−0,7; −0,1]) проходит тест Middle: честно, с поиском ответов на стороне (на
незнакомых вопросах уходит со вкладки, копирует вопрос, вставляет числовой ответ) или выучив ответы
3 слитых вариантов; ложные срабатывания меряются на честных уровня Middle:

| Группа | Риск → подтверждающая форма | Сдали: только детектор утечки | Сдали: + проверка поведения |
|---|---|---|---|
| Честные, уровень Middle | **0,0%** | 85,8% | 85,8% |
| Честные, уровень Junior | 0,0% | 8,0% | 8,0% |
| Ищут ответы на стороне | **99,8%** | 51,5% | **0,3%** |
| Знают слитые ответы | **84,8%** | 18,2% | 11,7% |

### Надёжность, калибровка, скорость

Надёжность по длине теста (корреляция θ на параллельных формах): 10 заданий — 0,72; 15 — 0,81;
**20 — 0,85**; 25 — 0,86. Поэтому выбрана длина 20 (≈ 10–15 минут).

Калибровка: по 1 500 симулированным прохождениям трудности заданий переоцениваются по ответам;
RMSE относительно истинных b падает с 0,30 (экспертные уровни) до 0,17 — банк самоулучшается по мере
накопления данных.

Скорость (одно ядро, без БД): генерация индивидуального варианта — 0,2 мс, оценка попытки (EAP,
person-fit, детектор утечки) — 3 мс.

Ограничения: симуляция предполагает одномерную способность внутри специализации и модель времени
ответа; реальная калибровка и пороги проверки поведения уточняются на пилоте (процедура и скрипты
готовы). Полный отчёт: `evaluation/results/tests_report.md`.

## 8. Регулярные задания (`services/tasks_service.py`)

ТЗ: «система периодически предлагает кандидату короткую задачу от работодателя — решить её или
предложить подход». Заказчик уточнил: адресно, формат челленджа на категорию не запрещён, способ
оценки — на усмотрение команды.

**Форматы.** «Решить» — конкретный ответ (число с допуском или короткий текст из списка допустимых),
проверяется автоматически сразу после отправки. «Предложить подход» — свободный текст, который
работодатель оценивает по рубрике из трёх критериев: корректность, полнота (крайние случаи,
ограничения), обоснование компромиссов — по 0–2 балла. Для сортировки откликов система ставит
предварительную оценку: долю ключевых идей работодателя, найденных в ответе (по основам слов, RU / EN),
и показывает, какие идеи упущены. Ключевые идеи кандидат не видит; итоговая оценка — работодателя.

**Кому.** «Адресно» — система предлагает задание подходящим кандидатам по одному; «челлендж категории» —
открытая задача для всей категории (специализация, при желании грейд), по желанию. Работодатель может
и лично предложить задание кандидату из подборки.

**Правило предложения.** У верифицированного кандидата не больше одного открытого предложения, новое —
не чаще раза в 7 дней (`TASK_OFFER_INTERVAL_DAYS`). Задание выбирается по сумме: соответствие грейду
(свой грейд — 2, соседний — 0,5, остальные не предлагаются), **работодатель рассматривает кандидата
для потребности, к которой привязано задание** (+2 и процент совпадения), задание проверяет
компетенцию, которую тест подтвердил слабо (+1 − балл), новизна задания, нагрузка работодателя на
проверку (`max_offers`). Кандидат видит, почему ему предложено именно это задание; предложение
истекает через срок задания (по умолчанию 7 дней), отклонённое повторно не предлагается.
Предложения создаёт фоновый проход раз в час и открытие кандидатом раздела «Задания» или кабинета.

**Что даёт результат.** Профиль отмечается актуальным (компонент «актуальность» в подборке), на
карточке кандидата у работодателя — сигнал «Задания: 3 · средний балл 83%», в объяснении подборки —
«Свежий сигнал: задание „Идемпотентность платежей“ — 83%, 3 дня назад». **Грейд задания не меняют**:
официально его присваивает только тест.

## 9. Дизайнеры: как тестировать объективно (концепция)

Заказчик допускает дизайнеров в справочнике, но приоритет — техническим ролям. Механика переносится
без изменений (банк → blueprint → IRT → правила грейдов), меняются форматы заданий — только с
объективной проверкой:

* **Эвристическая оценка макета:** скриншот интерфейса с заранее внесёнными дефектами (контраст,
  выравнивание, иерархия, состояния ошибок); кандидат отмечает области — балл по точности и полноте
  относительно эталонного списка дефектов.
* **Расчётные задания** (параметрические семейства, как у разработчиков): контраст по WCAG для пары
  цветов, отступы в 8-pt сетке, типографическая шкала, размер области нажатия.
* **Дизайн-системы и доступность:** токены, состояния компонентов, auto-layout, требования WCAG —
  закрытые вопросы с одним ответом.
* **UX-исследования и метрики:** интерпретация A/B-теста, расчёт SUS, воронка конверсии — числовые
  ответы.
* **Портфолио** — экспертная рубрика как атрибут профиля, не влияющий на грейд (субъективно).

Компетенции специализации «UI/UX-дизайн»: визуальный дизайн, UX и исследования, дизайн-системы,
доступность, прототипирование — с теми же квотами в blueprint.
